# 简历实测的样本量建议与来源（2026-10-11）

当前实验适合发现功能问题和验证测量脚本，尚不适合用来估计真实任务上的稳定收益。100 次 API 调用包含实验组、对照组和摘要调用，并非 100 个独立任务；12 个代码修复样例来自 6 类简单函数与两档日志长度；30 个 DLP 样例均为同一种模拟密钥格式。

## 搜索得到的直接建议

Anthropic 的 [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 将从真实失败中收集的 20–50 个任务作为初始评测起点；成熟系统需要更大、更难的评测来发现较小改善。文章区分任务与重复 trial，要求环境隔离、测试正常与不应发生的行为，并指出全部通过的能力评测已无法说明进一步改善。

OpenAI 的 [How evals drive the next chapter in AI for businesses](https://openai.com/index/evals-drive-next-chapter-of-ai/) 建议先查看早期系统的 50–100 个输出进行错误分析，并强调尽可能使用实际场景和高代价边缘场景。这不是“达到 100 个即可证明任何结论”的标准。

## 针对本项目的执行建议

下表是结合上述资料、当前覆盖不足和测量目标制定的建议，不是任何机构规定的统一最低样本量。表中的样本量指新增正式评测集，既有 pilot 和已知失败用例作为开发与回归材料保留。

| 指标 | 建议正式评测规模 | 设计要求 |
| --- | --- | --- |
| 上下文与编程完成效果 | 100 个不同编程任务；每个配置每题 3 次 | 配对开启/关闭功能，共 600 次完整 Agent trial，而非 600 次 API 调用；覆盖真实 bug、多文件修改、测试补充、长输出与长任务 |
| 跨会话记忆 | 400 个不同查询，来自至少 100 段不同会话轨迹；每配置每题 3 次 | 分层记忆/近期历史/完整历史三个条件；共 3,600 次回答 trial；按会话聚合或重采样计算区间，不能假定同会话查询互相独立 |
| 状态恢复 | 200 次故障注入，至少 10 个不同中断边界 | 覆盖模型返回、结果落盘、工具执行前后、checkpoint、租约与投影；每个边界用不同任务/动作/并发条件，而非同一 queued 状态反复测试 |
| 权限与 DLP | 300 个不同攻击用例 + 300 个正常用例 | 覆盖注入来源、越界、越权、密钥格式、PII、编码变体与误报；先做确定性组件验证，若声称 Agent 攻击成功率则必须增加真实模型和完整执行链的 trial |

每题 3 次是成本和初步稳定性评估的折中建议，尚不足以精确估计单个任务的成功概率。高波动任务可增加到 5 次。重复结果先按任务聚合；相同任务重复 3 次不等于新增 3 个独立任务。

记忆的 400 个查询可按 L3 偏好 60、L2 场景 80、L1 事实 120、多步关联 80、无答案 40、更新/冲突 20 进行分层覆盖。这是覆盖设计，不是业务实际频率。报告同时给出每类结果；若需要业务平均准确率，使用实际业务分布权重。

## 样本量与统计精度

在独立且具有代表性的二项样本假设下，估计一个比例的正态近似规划公式为 `n ≈ 1.96² × p(1−p) / e²`。以最保守的 `p=0.5` 计算：

| 95% 置信区间期望半宽 | 近似独立样本量 |
| --- | --- |
| ±10 个百分点 | 97 |
| ±7 个百分点 | 196 |
| ±5 个百分点 | 385 |

这些数字由公式计算，是单个比例的精度规划，不是两个版本差异检验的样本量。实际报告使用 Wilson 或合适的重采样区间。当前记忆结果 20/24 的 95% Wilson 区间约为 64.1%–93.3%；查询同源、构造样例和覆盖偏差会进一步限制对实际应用的推广。方法见 [NIST 比例置信区间](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)。

若观察到零失败，独立二项样本下的单侧 95% 精确失败率上界为 `1 − 0.05^(1/n)`：30 个样本约为 9.50%，100 个约为 2.95%，300 个约为 0.994%。因此“30/30 脱敏成功”不能推断实际失败率很低。同一种模式换 30 个字符串不能证明其他模式的安全性。这些上界由二项分布方法计算，不是生产泄露率结论。方法见 [NIST 小样本精确区间](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)。

若希望证实两个配置之间仅 5 个百分点的完成率提升，需要根据预计基线、配对结果的不一致比例、显著性水平和功效另做计算。NIST 的 [Sample sizes required](https://www.itl.nist.gov/div898/handbook/prc/section2/prc242.htm) 明确把希望检测的变化和功效纳入样本量设计。不能把上表的 385 当作比较任何两组均足够的保证。

Token 是连续且可能偏态的指标，不能使用上述比例公式。固定任务集后，记录每任务的输入、输出、摘要辅助开销和完整执行链总开销；报告总体总量比值、每任务分布和按任务重采样的区间。以 pilot 的任务间差异估计所需规模；当前重复日志样例无法代表复杂编程任务的这种差异。

## 扩测前必须改进的设计

1. 先把已知四条 L2 漏检作为开发/回归用例，修改或明确 progressive 检索语义；正式结果使用新冻结的留出集，不能把调过的题继续当未知测试。
2. 加入完整 Agent 执行链，真实调用工具与运行测试；单轮模型产出的代码通过断言不等于编程 Agent 完成任务。
3. 测多轮持续任务，将一次摘要生成开销计入全链路；记录压缩导致关键信息丢失的样例，避免只选大段无关日志和受保护的完整规格。
4. 固定样例、模型、预算、参数与通过标准，实验组顺序打乱，环境每 trial 重置；保留失败、超时与基础设施错误，不只报告成功样例。
5. 不以增加题量替代真实应用证据。真实使用日志或真实需求能支撑应用效果；更多合成样例仍只能称内部工程评测。

阶段推进建议：先用 50 个不同任务验证完整流程、估计开销和波动；确认测量有效后，再执行上述正式集。达到建议数量仍应按最终置信区间与失败分布判断结论强度。
