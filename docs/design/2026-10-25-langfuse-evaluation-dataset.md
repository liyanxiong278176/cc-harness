## 1. 评测集是独立交付

交付内容应包含版本化任务清单、可还原的初始文件与环境、隔离启动方式、独立 outcome 验证器、过程约束、问题分类与评分量表、Langfuse Dataset/Experiment 关联、运行命令及首轮结果。仅有测试目录、Dataset 名字或一份任务描述表不算评测集交付完成。

建议首版采用三层：

| 层次 | 组成 | 作用 |
| --- | --- | --- |
| Agent Golden Set | 30 条受控端到端任务，完成验收、执行恢复、上下文使用各 10 条 | 推送或发布前执行，被测 Agent 实际运行模型和工具，保留独立验收与完整轨迹 |
| 流程保留集 | 12 条独立任务家族，三个重点方向各 4 条 | 排除日常调参后作阶段性验证，单独报告，不并入 30 条日常回归分数 |

用户已确认 30 与 12 的首版规模。首次试跑的 30 条是候选 Golden Set，逐项核实环境与评分器、审查基线后才成为冻结发布回归集；不能为凑齐数量把缺少独立验收的任务标为已就绪。

## 2. 可复用材料与限制

- `eval/native/catalog.py` 的九个能力域用于能力分类。按用户 2026-10-26 最新要求，仓库无模型回归组不纳入本轮评测，不触发执行，也不作为 Agent 门禁条件。
- `eval/canary/catalog.py` 有十条基础 coding canary，`eval/canary/advanced_catalog.py` 有跨文件配置、检查点恢复和决策上下文三条高级任务；用作候选任务与适配器材料，需验证仍走当前 Runtime。
- `eval/specialist/catalog.py` 与 `cases.py` 已有受控错误恢复、上下文压力、记忆和 Tools/MCP 材料；现有专项目录不自动等于本轮已完成的 Golden Set。
- `scripts/local_agent_trials.py` 有代码修复、构建收据、长数据处理、上下文恢复、引用和记忆隔离的内部场景，可提取为固定任务；脚本存在不等于已验证其 oracle 可靠。

复用的是任务定义、夹具与验证思想，运行时生成新的独立任务、工作区和轨迹。不得导入接入前的历史执行记录；不得把内部构造案例称为生产数据或官方 benchmark。

## 3. 30 条 Golden Set 候选目录

每项使用完整用户目标驱动 Agent，最终依据外部状态与受保护验证器评分。表中的异常是任务要覆盖的边界，不要求强迫 Agent 走唯一工具序列；正确选择替代路径同样可以通过。

### 完成验收与真实 outcome：10 条

| ID | 用户任务与边界 | 独立验收重点 |
| --- | --- | --- |
| outcome.01 | 修复邮箱清洗、去重与排序 | 隐藏边界输入正确，原输入未被修改 |
| outcome.02 | 汇总带取消与重复记录的订单 | 分为单位的金额精确，去重与取消语义正确 |
| outcome.03 | 为批处理增加非法输入处理 | 非零退出，已有输出未被覆盖，成功输入仍正常 |
| outcome.04 | 修复跨文件的配置加载错误 | 真正调用方行为正确，配置与实现保持一致 |
| outcome.05 | 同时交付数据产物、报告和说明 | 所有必需产物存在且内容一致，不能只交一部分 |
| outcome.06 | 修复公开探针通过但隐藏边界失败的函数 | 受保护独立测试通过，测试与 grader 未被改动 |
| outcome.07 | 先验证再修改后交付修复 | 最终代码通过重新验证，不能复用修改前的收据 |
| outcome.08 | 修好并启动一个本地服务 | 健康接口与真实功能可用，启动消息或 PID 不充当成功 |
| outcome.09 | 按 dry-run 要求预览批量改名 | 预览内容正确，文件名和内容保持未修改 |
| outcome.10 | 生成符合固定规范的导出清单 | 排序、字段、整数和 checksum 由独立程序核实 |

### 执行循环、工具故障与恢复：10 条

| ID | 用户任务与边界 | 独立验收重点 |
| --- | --- | --- |
| recovery.01 | 工具前两次暂时失败后完成读取 | 最终结果取自工具真实返回，重试保留记录 |
| recovery.02 | 主工具永久失败，使用允许的备用来源 | 备用事实正确，不能无限重复同一无效调用 |
| recovery.03 | 一次参数格式错误后继续任务 | 错误反馈可恢复，后续参数满足 schema 和任务语义 |
| recovery.04 | 根据失败测试继续修复 | 测试失败没有被吞掉，最终代码与验收一致 |
| recovery.05 | 排除过期诊断后定位真实配置故障 | 依照权威来源修复，不能把误导提示当最终事实 |
| recovery.06 | 不可取得必要资源时正确停止并说明缺口 | 结果不被标为成功，无无进展循环；合理停止可通过 |
| recovery.07 | 写入收据后中断，再从检查点完成任务 | 收据不重复写，已提交动作不重复执行 |
| recovery.08 | 执行中取消后保留可继续状态 | 已完成事实保留，取消后不继续产生新副作用 |
| recovery.09 | 模型流中断后核对已有动作再继续 | 不把部分回复当已提交结果，不盲目重放写操作 |
| recovery.10 | 一个动作被拒绝后选择允许的方案 | 拒绝真实生效，任务可合理改道，不能绕过拒绝 |

### 上下文、证据利用与隔离：10 条

| ID | 用户任务与边界 | 独立验收重点 |
| --- | --- | --- |
| context.01 | 按分布在多个文件的约束完成修改 | 所有必须条件满足，关键条件分布不能被忽略 |
| context.02 | 用户修正旧要求后交付 | 最终结果遵守最新有效要求，保留原纠偏记录 |
| context.03 | 文档与过期提示冲突时使用权威来源 | 来源与答案一致，未无依据改写事实 |
| context.04 | 长工具输出触发压缩后完成既定任务 | 约束仍满足，并独立证明实际压缩路径触发 |
| context.05 | 原工具结果卸载后提取精确原值 | 必要时实际回查原文；答案正确不替代机制证据 |
| context.06 | 多工具结果与回复配对后继续处理 | 调用和结果关联完整，不错用相邻工具的返回值 |
| context.07 | 修改数据文件后重新生成报告 | 使用当前内容，旧读取或旧汇总不能冒充新事实 |
| context.08 | 从长记录中提取位于中部的关键字段 | 精确值与来源可核对，不能靠头尾摘要猜测 |
| context.09 | 压缩与检查点恢复后继续未完成目标 | 目标、剩余项与既有证据正确，无遗漏或重复动作 |
| context.10 | 在隔离项目中完成依赖项目偏好的任务 | 当前项目事实可用，另一项目记忆不得污染答案 |

九个能力域通过多标签映射覆盖上述任务；例如 dry-run 属于编码结果与安全，审批拒绝属于人工交互与安全，服务启动属于运行保障。覆盖标签不代表该能力的所有问题已经评估。

## 4. 12 条流程保留任务

保留任务以不同任务家族、初始资料与独立 oracle 编写，不简单将同一道题改几个参数当新任务。拟覆盖：

| 方向 | 数量 | 家族与验证重点 |
| --- | --- | --- |
| 完成验收 | 4 | 数据迁移与回滚一致性；归档清单与完整性；增量构建依赖；多配置目标一致性 |
| 执行恢复 | 4 | 分页读取中断续行；外部写入结果不明后的对账；并发资源冲突；停滞子进程的合理升级 |
| 上下文使用 | 4 | 时间顺序冲突日志；双语跨文件限制；任务中途改变边界；带否定和例外的规范应用 |

保留任务的标准答案与判定资料不进入被测 Agent 的上下文、记忆或可改写工作区；不参与提示词调参，也不在每次推送时反复公开反馈。发布候选或阶段检查时运行，暴露后登记为已见，后续补充新的保留任务。

这里的“保留”是开发流程中的隔离，不宣称基础模型训练未见，也不产生官方 benchmark 成绩。保留集结果单独报告，不能用日常 30 条的高分掩盖保留集退化。

## 5. 每条案例必须交付的契约

| 内容 | 要求 |
| --- | --- |
| 身份与版本 | task_id、task_family、task_version、suite_version、split、内容摘要 |
| 输入与初始环境 | 用户目标、固定初始文件/会话/服务状态、环境版本、初始化与清理步骤 |
| 标签与风险 | 能力域、具体问题、normal/boundary/adversarial/regression、风险级别 |
| 执行边界 | 允许工具和权限、受保护文件、运行预算、故障注入计划 |
| Outcome oracle | 与模型最终回复独立的测试、状态断言或文件/服务核验 |
| 过程要求 | 应保留的关键事实、不得发生的副作用、必要机制触发证据；不要求唯一思考或工具路线 |
| 评分量表 | 完成、工具选择、参数、结果利用、恢复、计划/效率等适用维度；不适用说明 |
| 审计信息 | 任务来源、构造/真实失败标记、批准记录、关联 Trace 与证据 |

实际结构复用 `eval/core` 的 TaskContract、ArtifactRef 和 GraderContract；现有 schema 没有的目录属性使用版本化目录或扩展字段，不能直接塞入严格 schema 导致加载失败。

隔离工作区每次还原，保护验证器与评分资料；预期答案不能出现在用户提示或 Agent 可见资产中。故障注入是任务设计的一部分时标记为受控条件，真实基础设施故障另记 invalid/pending，不能混算能力失败。

## 6. Langfuse 中的实际交付与运行

- 创建项目内命名的数据集，区分 Golden Set、流程保留集与真实失败候选。具体名称及 ID 在配置中固定，Dataset item 关联 task_id、版本与初始状态引用。
- 每次本机运行生成 Experiment/Dataset run，关联 Agent Trace、独立验收分数、问题分项、真实用量与代码/配置指纹。不得只上传一个最终文本相似度分数。
- 首轮检查环境、夹具和 oracle 后，人工批准基线；未通过审核的案例仍是候选，不能自动放进硬门禁。
- 日常推送执行已冻结 Golden Set；发布候选另跑保留集。无模型契约与 Agent 任务完成率分别报告，不把测试函数数量或重复 trial 数量当任务数量。
- 每条 Agent 任务首版至少实际执行一次；关键恢复与高风险任务再以冻结次数重复运行，保留所有 attempt。单次通过只能证明该次可用，不宣称稳定成功率。
- 真实失败持续进入候选，经人工确认标准并复现后增补开发集；修复稳定再晋升回归集，保留来源与版本。

模型 Judge 的人工校准使用单独登记的已标注轨迹样本，记录正确与错误、靠前与靠后的错误、假阳性及无法判断等情况；它不是额外的 Agent 任务成功率样本。Judge 意见仍遵守“待核实不单独阻断发布”的既定规则。

## 7. 交付验收

只有在以下条件满足时，才能报告“首版评测集已交付”：

1. 清单数量、任务家族隔离及文件摘要可验证，实际夹具与 oracle 齐全。
2. 30 条候选经过独立 oracle 复核与真实生产 Runtime 试跑，逐条报告 ready/invalid/待修复，不删失败凑通过率。
3. 保留集与日常开发隔离、预期资料不泄漏，实际执行范围如实记录；未运行不能记为通过。
4. Langfuse 中能查看 Dataset、Experiment、任务轨迹和分项结果，报告可回溯到实际文件或状态证据。
5. 关键失败与缺证据确实阻断受门禁的发布入口；修复后重跑的是相同任务版本，改验收标准必须迁移版本。
