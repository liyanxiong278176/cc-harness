# WebUI 重设计交付记录

日期：2026-10-24。依据：[已确认契约](2026-10-23-webui-redesign-contract.md)。

## 实现

整体界面采用石墨灰、克制蓝色强调和统一的深浅主题；项目/会话树、对话/轨迹切换及按需右栏形成新的工作区。重放旧文件修改事件不会自动打开右栏，新会话默认收起详情。

对话展示紧凑执行过程、真实计划清单、文件变更摘要和独立最终回复。工具参数与长输出按需展开，失败记录保留提示。轨迹支持工具/异常筛选、搜索、结果展开、耗时和事件详情。

文件差异接口读取不可变工具证据；原生文件工具使用已提交的 diff，终端工具使用有界文本采集。缺少前后文本、二进制或超出采集边界时明确说明不可用。终端执行窗口同时发生的外部编辑可能包含在内，界面显示来源说明；这与直接把工作区 Git 差异归为模型修改不同。

WebUI 普通运行中新消息统一进入会话根 FIFO，保留当前审批；修改与撤回只针对未认领的消息。认领事件和预期事件序号保护开始执行与修改的竞争，已开始的消息不能撤回。队列逐条释放，避免后到消息并行越过前项。

审批就地展示操作命令与范围，设置、权限、本地能力/记忆、运行详情和文件预览使用同一视觉系统；支持窄屏和键盘焦点。供应商私有推理不在界面中展示。

## 使用边界

历史任务无足够文件证据时不能补出可靠差异。当前终端内容采集为允许的文本后缀、单文件 256 KiB、每次快照 16 MiB，仍保留其他文件的原有哈希证据。文件预览显示当前内容，差异显示对应工具操作的历史内容，两者明确分开。

当前变更保留在工作区供审阅，未创建 Git 提交或发布到外部环境。

## 后续请求任务列表修复

修复任务列表和执行计划固定读取首轮请求的问题。会话接口单独返回当前执行请求的 `task_run_id` 与 `task_projection`；前端从完整事件树选择已开始的后续请求，并仅应用该请求的任务增量。排队中的消息不提前替换当前任务，列表保持打开时也可切换到后续请求。

## 任务列表展示模型规划，而非用户原话

此前用真实目标替换自动根任务标题仍不符合任务列表的产品含义。本节取代上述标题回填的展示规则：自动根任务、自动 follow-up 任务及已移除的步骤不作为执行计划显示；没有模型规划时明确显示“尚未生成执行计划”，不编造细分任务。

补齐 `task_plan` 到持久任务条目的链路。模型提交每步的标题、依赖、验收条件和状态；`PlanNode.title` 可选持久化，空标题不改变旧计划序列化及摘要。Worker 启动步骤时保留模型标题，模型更新步骤状态后同步产生 Todo 事件；已完成步骤受现有重规划约束保护。多步任务提示明确要求先规划并随工作与验证更新，一步操作和问答无需强行拆解。

另一个根因是默认 core 工具包原先遗漏 `task_plan` 和 `task_wait`，导致模型实际上收不到规划工具。现已加入核心工具集，并以实际 `_build_tool_runtime()` 输出作回归断言。端到端本地模型测试也改用生产核心工具清单与契约，逐次断言模型可见 `task_plan`。

`scripts/verify_model_task_plan.mjs` 与 `scripts/preview_model_plan_worker.py` 验证模型调用 → 生产 Worker → task_plan → Todo 持久事件 → SSE → 刷新恢复的完整链路，没有直接写入 Todo 测试数据；确定性本地模型先提交三步计划，再真实读取项目说明，然后更新第一步完成及第二步进行中。不调用远程模型服务，不代表已评估真实模型规划质量。

截图：[等待真实计划](screenshots/2026-10-24/09-waiting-for-model-plan.png)、[模型提交三步计划](screenshots/2026-10-24/10-model-generated-task-plan.png)、[模型更新执行状态](screenshots/2026-10-24/11-model-plan-live-progress.png)。[端到端结果](screenshots/2026-10-24/model-plan-verification.json)。已有用户会话的只读浏览器验证也已更新：未持久化过模型计划时，刷新后仍显示明确空态，不再显示用户原话；见[当前旧会话](screenshots/2026-10-24/12-existing-session-no-fabricated-plan.png)。

相关模型、计划图、投影重建/兼容、Worker 恢复及规划工具回归通过，前端 11 项测试、生产构建与 Ruff 检查通过。列表按模型计划节点顺序展示。3080 服务已在当前任务确认暂停到检查点后重载；随后恢复同一活动 Run，API 确认恢复 running，未通过新建任务替代它。

运行时复核：恢复后的真实模型调用随后返回了不完整的 Write 工具参数 JSON，任务进入 failed_recoverable（KernelProtocolError），不是已完成或仍运行。已有文件和进度保留，没有绕过参数验证或持续自动重试。该任务尚未持久化有效细分计划，界面维持明确空态；本地模型规划链路测试通过不代表该真实模型调用成功。

## 继续按钮直接恢复执行

恢复使用 `/resume` 控制接口，立即显示“正在恢复…”并禁用重复点击，不调用 `/api/messages`。后端返回实际执行 Run 与状态并唤醒调度器；控制原因使用 `webui.resume`，历史 `WebUI 用户继续` 也不再作为用户气泡显示。模型上下文中的此类事件改为内部恢复控制，不增加用户指令；用户主动输入的补充要求仍保留。

新增并发回归复现：同一客户端同时启动调度器时，失败的初始化曾关闭成功初始化使用的模型连接。现在项目客户端创建/配置切换及调度器启动/关闭均串行化。配置变更检查同时考虑活动子任务，避免根任务已结束时关闭仍执行子任务的模型连接。

`scripts/preview_resume_control.py` 使用真实 LocalSupervisor、Worker 与文件读取执行器，浏览器实际点击 Continue 后验证已提交工具观察、处于 running、显示暂停按钮，同时确认一次恢复 POST、零消息 POST、刷新后无控制消息气泡。见[按钮即时反馈](screenshots/2026-10-24/13-continue-immediate-feedback.png)、[直接执行而不发送消息](screenshots/2026-10-24/14-continue-runs-without-user-message.png)与[验证结果](screenshots/2026-10-24/resume-control-verification.json)。测试不调用远程模型。

3080 实际会话也已验证：在当前任务处于 failed_recoverable 时更新服务，通过 Continue 接口恢复同一活动 Run，随后确认 running 和新增工具执行记录；没有提交 `/api/messages`。历史被误存为 TaskGuidanceReceived 的系统续跑文字也从聊天展示中排除。后续复核使用只读观察模式，不重复恢复运行中的任务。见[当前会话实际恢复截图](screenshots/2026-10-24/15-existing-task-resumed-without-message.png)与[实际会话结果](screenshots/2026-10-24/existing-resume-verification.json)。相关 WebUI、持久执行、暂停恢复、follow-up 回归、前端 12 项测试、生产构建及 Ruff 检查通过。

## 规划工具失败造成的阻塞修复

真实工具分发原先只给子任务工具注入 `run_id`，遗漏 task_plan/task_wait，导致调用绑定阶段 TypeError，被记录为 outcome_unknown。现已补齐参数，并增加通过 `_execute_tool` 的实际分发测试；模型规划浏览器验证也改用此分发器，避免绕过真实调用入口。

已有阻塞经 `scripts/reconcile_plan_dispatch_failure.py` 严格核验：唯一未知动作必须为只读 task_plan、TypeError、参数可解析，缺失 run_id 的绑定错误可复现，动作开始至异常之间没有 Plan/Todo 写入。核验后以审计 artifact 将该动作纠正为 failed，未将它伪装成成功，也未执行用户工程文件操作。更新服务并恢复后，已确认未知动作归零、同一任务 running，出现新的调度和工具执行事件。见[实际恢复截图](screenshots/2026-10-24/16-blocked-task-recovered.png)与[审计验证](screenshots/2026-10-24/blocked-task-recovery-verification.json)。

对其他尚未核对的未知结果，恢复接口给出明确原因且不重新排队；状态提示明确“需要先核对结果”，不再承诺直接继续。普通可恢复阻塞仍保留继续入口。相关工具分发、未知动作恢复、WebUI 与 Worker 恢复回归及前端 13 项测试通过。
