# Vendor a pinned DeepSeek UI source snapshot

cc-harness will vendor the DeepSeek Harness UI dependency closure at the reviewed commit `c291e7961a515f6d7af9304e7fd1d257929aef26`, preserving the required license and third-party notices and building it from the repository without network fetches. The closure includes the complete Web presentation layer and only the client-side layout, session, conversation, editor, state, and store/tool dependencies required to run it; it excludes the upstream Agent Runtime, CLI, benchmark, native clients, and unrelated documentation. The existing cc-harness `web/src` page implementation will be removed, while the existing Vite project remains the sole build entry and emits the assets consumed by the Python WebUI server. The pinned upstream source will live under `vendor/deepseek-ui/` with its original layout, commit and notices; cc-harness entrypoints, backend adapters and narrowly scoped overrides will live under `web/src/cc/` and be connected with Vite local aliases, keeping provenance and upgrade diffs visible. UI dependencies will be consolidated into the existing `web/package.json` and pinned by `package-lock.json`; installation may use an explicit network/cache step, but the build itself must not fetch dependencies implicitly, and clean-install, license and security checks are required. A backend Web compatibility facade will translate the migrated UI's queries, commands, and streams into the existing cc-harness Runtime, session store, permission gates, and immutable events; it will not create a second execution or state engine. REST remains the command/query boundary and replayable SSE remains the live event boundary; reconnects use event sequence cursors. The facade will be exposed as a versioned Web compatibility surface so existing `/api`, TUI, headless JSON and SDK clients remain compatible; schema changes require migration and regression evidence rather than silently changing shared routes. The facade will publish a capability manifest so unsupported upstream controls are visibly disabled with an explanation rather than simulated. The migrated sidebar will map project roots to sessions to runs/tasks using server projections and stable IDs, never browser-owned shadow state. Approval controls will submit decisions for one pending tool action; a rejection is persisted as a tool result and returned to the model so the Run can continue or replan, while explicit stop, hard policy denial, and unrecoverable errors remain terminal. The UI will expose a compact Runtime status and context summary, with expandable details for context accounting, memory retrieval/compression and security decisions; values remain unknown when the Runtime has no authoritative evidence. Memory injection remains Runtime-owned: each Run starts with L3 project memory and expands on demand in L3 → L2 → L1 → L0 order, with retrieval and injection evidence shown in the details view. Context compaction remains Runtime-governed before a model request when the effective window requires it; immutable compaction events expose start, completion or failure, and the UI never truncates or invents token savings. On page load, refresh or SSE disconnect, the UI will reload the projection and replay from the last event sequence; conversational “继续” remains the user-facing recovery trigger and is interpreted by the main Agent using checkpoint facts, while lease conflicts are shown as an explicit read-only/recovery state. The migration will retain cc-harness branding and replace upstream brand marks or unclear-rights artwork, while preserving the upstream license, third-party notices, and reviewed commit in a vendor notice. Model settings will be server-owned and accessed through a controlled settings API; the UI may reveal the API key only on explicit user action, while the key is excluded from events, prompts, logs, SSE and browser persistence. Conversation bubbles will render only user-facing Markdown/text; completion envelopes, evidence JSON, internal event names, scheduler fields and provider protocol remain in expandable runtime/audit details, and tool cards derive their status from projections rather than model claims. User-facing responses will default to simplified Chinese while preserving commands, paths, stack traces, protocol fields, and provider errors verbatim; an explicit user language request overrides the default without changing Runtime facts. Project selection will use a local directory picker backed by server-side path normalization and validation; the composer cannot create a session or submit a Run until a valid project root is selected and available, and path errors remain visible rather than being silently coerced. The three composer policy modes will map to server-enforced Runtime policies: per-action approval, risk-only approval, and automatic approval within the sandbox, all still subject to hard-deny, project-root, network/credential and audit boundaries; the active policy is recorded with the Run. Within one project, one Supervisor lease elects the scheduler while multiple sessions retain independent Run and worker leases; resource-scoped locks or isolated worktrees protect overlapping writes without turning unrelated sessions into a permanent queue. The Stop control cancels only the active Run's new work and in-flight tools, persists cancellation/checkpoint evidence, preserves the session, and allows a subsequent natural-language message to trigger a state-aware follow-up; it never deletes evidence or kills other sessions. The `cc-harness` command will serve the built Vite assets from the local Python WebUI and print the actual loopback URL; separate Node dev hosting remains development-only and browser auto-open is optional via an explicit flag. WebUI is the default and complete control plane; TUI remains an explicit compatibility and diagnostic interface over the same Runtime/API/event facts and does not introduce a second state store. The migration release gate will require a clean Vite build, Web facade contract tests, real-browser flows for project/session/message/approval/stop/reconnect/context/memory/security/settings, and visual regression against the reviewed DeepSeek reference; evidence must show event cursors, no raw protocol bubbles, no secret leakage, no implicit network build, and honest unknown/error states. cc-harness remains authoritative for Runtime, sessions, events, checkpoints, permissions, context, memory, and safety. A pinned source snapshot is chosen over npm packages because of release-version skew and over a submodule because of clone/CI/offline fragility; upgrades require an explicit compatibility and visual-regression review.
