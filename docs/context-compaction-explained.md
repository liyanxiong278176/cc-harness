# 上下文压缩:为什么 LLM 需要"健忘",以及怎么健忘

> 写给**所有人**——不需要编程背景也能看懂

---

## 一句话总结

> 上下文压缩 = **对话太长装不下时,自动把旧的"打包"或"扔掉",给新的腾位置**。

---

## 为什么需要它?一个真实场景

想象你和 AI 助手聊天:

```
你: 帮我写一个 Python 函数,计算斐波那契数列
AI: (写了 fib 函数)
你: 加个类型注解
AI: (加了)
你: 加个测试
AI: (写了测试)
你: 跑一下
AI: (输出测试结果)
你: 提交到 git
AI: (git diff 输出)
你: 加个 README
... (继续聊了 50 轮)
```

第 51 轮你想让它"继续优化",它**突然失忆**了——忘了你之前要求的所有细节。

**为什么?** LLM 有一个"工作记忆容量"(叫 context window,默认 20 万 token,约等于一本 500 页书)。聊得太多,前面就被**挤出**窗口外,AI 看不到,就"忘了"。

---

## 一个生活化的类比

把 LLM 想象成一个**很聪明但脑子只有这么大**的人:

```
你的对话 = 一摞草稿纸
脑子容量 = 桌子大小(草稿纸多了放不下)
```

解决问题有 3 种办法:

| 办法 | 类比 | 优缺点 |
|---|---|---|
| **不压缩,扔旧草稿** | 把写满的草稿纸撕掉 | 简单,但丢信息 |
| **压缩旧草稿** | 把 10 页笔记浓缩成 1 页"要点" | 保留信息,但要花精力(AI 要重读) |
| **混合** | 先撕掉不重要的,再压缩剩下的 | 既省空间又不丢关键信息 |

cc-harness 选了**第 3 种**——混合策略,分 4 个层级。

---

## 4 个层级:从轻到重

cc-harness 把"对话占脑子比例"分成 4 档,根据压力自动升级:

```
对话占用比例
    0%         60%        80%        95%       100%
    ├───────────┼──────────┼──────────┼──────────┤
                ↑          ↑          ↑
               Tier 1     Tier 2     Tier 3
              "剪一点"   "剪更多"   "总结压缩"
```

### Tier 0 — 啥也不做 (< 60%)

```
脑子还很大,对话才占 50%,不用动。
```

### Tier 1 — 剪掉废话 (60-80%)

**干了什么**:把长文件输出截短,用户贴的代码块缩短。

**例子**:
```
之前: [完整 200 行文件输出]
之后: [前 30 行 + "...(共 200 行,截断)..." + 后 10 行]
```

**代价**:**零**——纯字符串操作,不需要 AI 重读。

### Tier 2 — 用占位符替换 (80-95%)

**干了什么**:工具输出变成"这里曾经有过文件输出",AI 的早期回答只剩第一句。

**例子**:
```
之前: "我执行了命令 ls -la,输出如下: total 32 drwxr-xr ..."
之后: "[tool output, truncated]"
```

**代价**:**零**——还是纯字符串操作。

### Tier 3 — 让 AI 写摘要 (≥ 95%)

**干了什么**:**调一次 AI**,把老的对话总结成几段文字,替换进 messages。

**例子**:
```
之前: messages 列表里有 50 条对话(超长)
之后: 一条"摘要消息":{
  "用户最初的需求:写 Python 函数...",
  "AI 已完成的:加了类型注解、写测试...",
  "下一步:写 README"
}
```

**代价**:**1 次 LLM 调用**(花钱、花时间)。这是为什么 Tier 3 是最后手段。

---

## 保护带:最后 8K token 不动

无论怎么压缩,**最近 8K token(约 2000 个中文字)永远不压缩**。

**为什么?** 你现在正在聊的内容(比如"继续优化"),不能因为压缩就丢了。

类比:就像整理房间——**你正在用的书桌**永远不收拾,只收拾**书架**和**柜子**。

---

## 怎么控制它?环境变量

在 `.env` 文件里改这些数字,就能调压缩策略:

```bash
# 总脑子容量(默认 20 万 token)
CONTEXT_WINDOW=200000

# Tier 1 触发阈值:占用到 60% 才开始剪
CONTEXT_TIER1=0.6

# Tier 2 触发阈值:占用到 80% 替换占位符
CONTEXT_TIER2=0.8

# Tier 3 触发阈值:占用到 95% 才让 AI 摘要(贵的操作)
CONTEXT_TIER3=0.95

# 保护带大小:最后 8K 永远不动
CONTEXT_PROTECT_TOKENS=8192
```

### 实战调整建议

| 你的场景 | 建议 |
|---|---|
| 默认使用 | 啥也别改 |
| 任务很短(几轮对话) | 把 T1/T2/T3 调到很高(0.99),几乎不触发 |
| 想强制看到 Tier 1 效果 | `CONTEXT_TIER1=0.05`(5% 就触发) |
| 想看 Tier 3 摘要长啥样 | `CONTEXT_TIER3=0.10` |
| 完全禁用压缩 | 全部设为 `1.0` 或在代码里 `enabled=False` |

## 类比:不同人处理长对话的方式

| 人格 | 压缩策略 | 例子 |
|---|---|---|
| 记事本型 | 全记,从来不整理 | Claude Code 的 CLAUDE.md |
| 极简型 | 用完就扔 | 不压缩,但对话窗口会爆 |
| **分阶段型(cc-harness)** | 先扔垃圾,再压缩,保护当下 | **本文讲的** |

## 看不下去的可以只看这 3 行

1. **为什么压缩**:对话太长,LLM 脑子装不下,会"失忆"
2. **怎么压缩**:4 个层级——没事不干 / 剪短 / 替换 / 让 AI 写摘要
3. **保不保**:最后 8K 永远不压缩(你正在聊的内容)
