# 任务执行内核改造：设计访谈

状态：12 项行为已确认，用户已整体批准，代码改造与确定性验证已完成。

## 已确认范围

- 以用户提供的《第 4 章 任务：编排、长程推进与协作流转》作为执行与编排能力的目标参照。
- 改造对象为当前 Agent Runtime / Loop。
- 上下文、MCP、记忆及其既有行为保持不变；执行内核继续接入现有能力。
- 按 grill-with-docs 逐项澄清设计，并随已确认的术语和决策更新文档。

## 代码与既有决策依据

- `cc_harness/run_model.py`：Run 状态机、GoalContract、PlanGraph、EvidenceRef 与完成门禁。
- `cc_harness/worker.py`：持久交互循环、动作恢复、观察提交与完成证据检查。
- `cc_harness/coordinator.py`：任务提交、计划修订、子任务与候选结果验收。
- `cc_harness/capability_runtime.py`：现有上下文、记忆等能力的接入。
- ADR 0105：Runtime 可以在证据满足时主动生成完成候选；模型完成标记既非必要条件，也非充分条件。
- ADR 0106：项目状态由单一 Durable Runtime 写入。

上述仅为静态代码调查，不代表本轮已执行行为测试或证明所有目标能力已经满足。

## 已决事项 1：任务总预算（用户选择 A）

既有 `2026-08-18-durable-loop-capability-integration.md` 明确规定 Run 没有总 Token、费用、时长或调用次数上限。新参考文本要求步骤、时长、Token、费用、工具调用、子任务并发及高风险动作预算，并要求预算耗尽时产生明确结果与未完成清单。

支持多维预算，由任务或运行配置指定，未配置的维度仍无限；接近上限时收敛，耗尽时停止新增行动，保存证据和未完成清单，子任务消耗计入父任务总额。这替换旧规格中“不允许 Run 总预算上限”的原则，但不强加默认限额。

尚未确定具体状态迁移、阈值、计量口径、在途动作收尾和并行子任务预算预留机制。预算耗尽不得作为成功完成的证据。

## 已决事项 2：任务生命周期状态（用户选择 A）

采用章节中的业务生命周期：CREATED、RUNNING、WAITING_INPUT、WAITING_APPROVAL、WAITING_EVENT、PAUSED、VERIFYING、COMPLETED、FAILED、CANCELLED。排队、Worker 租约等作为独立调度信息，不能与业务生命周期混为一组状态。

现有 RunStatus 使用 awaiting_approval、waiting_on_predecessor、stalled、blocked、failed_recoverable 等状态，没有独立的 waiting_input、waiting_event、paused、verifying。旧状态的映射、历史事件兼容和 API 迁移方案尚待设计，不直接按名称强制映射。

## 已决事项 3：暂停与取消后的续行身份（用户选择 A）

PAUSED 可恢复同一 Run；CANCELLED 为不可恢复终态。用户在取消后要求继续时，创建关联的新 Run，引用已有成果并重新核验；保留旧 Run 的取消记录。取消不自动撤销已经发生的文件修改或外部副作用。

当前 coordinator.resume() 允许 CANCELLED Run 回到队列；interrupt() 也复用取消请求链路。实施时需要区分暂停与取消意图，并保留在途动作的真实结果或 Outcome Unknown。具体安全点与父子传播规则尚待细化。

## 已决事项 4：计划审批的默认策略（用户选择 A）

章节区分轻量 Todo、Plan Mode 和 Planner–Executor。当前 complete_plan_discovery() 可以提交计划并打开 mutation gate，不能仅凭存在计划探索阶段就认为已经实现人工审批后执行。

普通编码任务默认直接推进，按复杂度维护 Todo 或计划，在已有授权内修改；用户明确要求“先出方案”或规则要求审批时，先只读探索、提交计划并等待批准。任务复杂本身不意味着必须请求人工审批。

既有动作权限仍保持约束，计划批准不等于任意动作授权。显式 Plan Mode 下计划获批前不得修改目标工作区；计划与任务控制记录的持久化不属于被禁止的业务写入。后者的具体工具分类待实施设计。

## 已决事项 5：自动委派的默认策略（用户选择 A）

主 Agent 可以根据任务需要自行委派，不要求用户每次明确提出；简单任务自行完成，只有拆分有收益时才委派。子任务受主任务权限与预算约束，主 Agent 负责整合与验收，不能把整体完成责任转交给子 Agent。

当前已有父 Run 协调子 Run、动态任务契约、结构化子任务上下文、隔离写入和父任务验收等领域概念。具体并发、嵌套深度、失败传播及权限收窄规则尚待细化。

## 已决事项 6：执行中的用户追加消息（用户选择 A）

执行中收到针对当前任务的补充或纠正时，在安全的步骤边界处理，更新当前任务及计划；进度询问及时回答。不能继续按旧要求做完后才处理这些消息。

当前 coordinator.send() 将消息排入 follow-up 队列，既有 Follow-up Run 术语要求前序结束后创建独立 Run。实施时需要区分当前任务指导和独立后续任务；用户决定与目标变更必须记录为权威事实，不能仅写入提示或静默改写旧目标。消息分类、歧义处理和在途子任务同步规则尚待细化。

## 已决事项 7：前端断开后的默认行为（用户自定义）

关闭页面时后台继续；关闭终端时自动暂停，后续恢复原 Run，不视为取消。页面关闭后的后台任务遇到输入或审批要求时进入对应等待状态。

既有 Detached Local Run 的统一客户端脱离语义需要按页面和终端分别处理。终端退出不能只依赖进程退出回调，强制关闭后的暂停需要由存活的监督机制或恢复流程确认；在途副作用仍需保留真实结果或 Outcome Unknown。终端与运行的归属、多终端同时连接、机器关机及 Runtime 崩溃后的恢复策略尚待细化，不能据此暂停无关会话。

## 已决事项 8：验证失败后的默认行为（用户选择 A）

可修复的验证失败默认形成 Observation，由 Agent 在授权和预算范围内自行修复并重新验证，不要求用户批准每轮修复。遇到需要用户决定、权限边界、预算耗尽或持续无进展时停止自主推进，并明确说明缺口。

不得通过降低验收标准、移除失败检查或重复使用过期证据来获得完成状态。失败分类与无进展阈值待实现设计，现有完成证据门禁继续作为基础。

## 已决事项 9：用户纠正要求后的在途子任务（用户选择 A）

用户纠正影响已运行子任务时，在安全边界暂停受影响子任务，更新要求和任务契约后继续；无关子任务照常运行。不得等旧要求执行完才处理变更。

已发生的动作和旧版本成果仍保留来源，不假装已经撤销。旧目标或旧代码版本上的证据不能自动成为新目标的完成证据；需要重新核验适用性。子任务契约的版本化提交、在途动作核对和新旧结果竞争处理待实现设计。

## 已决事项 10：异常中断后的自动恢复（用户选择 A）

程序崩溃或电脑重启后，重新启动 Runtime 时自动找回进度和成果，但保持暂停，等待用户表达“继续”后再推进。不得因为进程重启而自动调用模型、派发工具或启动子任务，也不得自动恢复显式暂停或取消的任务。

用户继续后，先核对工作区、权限、剩余预算以及上次动作的实际结果，不直接重复结果不明的副作用。恢复投影、完整性检查与必要的状态记账可以先行，但不等同于业务任务自动续跑。

## 已决事项 11：旧任务迁移（用户选择 A）

新内核需要能接续改造前未完成的旧任务，保留记录与成果，核对状态后转换；无法确认之处暂停并说明，不猜测或重复执行。

现有 Run 绑定 Pinned Run Contract，运行时迁移要求无活动租约并提交显式迁移事件。上下文、MCP、记忆仍沿用原机制，不属于任务状态迁移的重建对象。

## 已决事项 12：预算耗尽后的任务状态（用户选择 A）

用户设置的预算耗尽时进入 PAUSED，保存进度、证据、已用额度和未完成事项；增加额度后可以继续同一 Run。不得标记成功，也不要求仅因预算耗尽另建任务。这明确调整参考章节中预算耗尽产生终态的要求。
